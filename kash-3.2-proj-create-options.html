Kash 3.2 · design options

Project creation — three ways in, two ways to plan

Decided so far: creation is container-first, one line to start. Ask for the client and derive the category. Personal is one Maintenance bucket plus the occasional real project. Dates start today with no end. The setup wizard is being retired.

Every mockup below is drawn to the 3.0 token spec — Figtree at two weights, 11/12/13/15/17 type, hairline borders, outline buttons, 3px category stripe, crimson reserved for status.

Part one

The create moment

All three options do the same thing: a project exists after one line and one keystroke. They differ in where that line lives, which changes how much the act costs you in attention.

Part two

The plan moment

You said the true shape is container-first: the project exists, then structure accretes. That means planning is not a thing that happens at creation — it's a mode you enter later, sometimes days later, and it needs its own front door. Two ways to build it.

Option D

Plan mode on the board

Same surface, different density. No new screen.

new task, Tab to indent
tab indent ⇧tab outdent ↵ new line ⌘↵ save and close

What happens

  • The Miller columns flatten into one editable outline. Tab and Shift+Tab move things between phase and task — the tree is built by typing, not by syntax.
  • Dates and estimates live in fixed right-hand columns, so setting them is never a separate step or a separate screen.
  • It replaces the wizard's Phases, Dates and Tasks steps with one surface, and it works identically on day 1 and day 40.

Trade

  • Real build: an outliner with keyboard tree editing is the most expensive thing in this document.
  • The board and the outline must agree perfectly or the toggle becomes a trust problem.

Recommendation

A + D, built in that order

Why this pair

Your two answers are in tension: container-first says make creation nearly free, but 1-2 phases with a start date says you do want structure early. A + D resolves it by separating the moments rather than compromising both — creation costs one line, and planning is a mode on the surface you were already looking at, available forever rather than only in the first ten seconds after creation.

Option D is also the only one that retires the composer's invisible grammar. Right now the tree is built by typing ;;; and Parent//+ Child, documented in one chip you have to click, taught wrongly in three places, and filed into a phase the composer never names. An outline where Tab means indent teaches itself.

Sequence

  1. Ship A alone. Two evenings. The wizard stays reachable from the overflow menu but stops auto-opening, so nothing breaks while D is built.
  2. Build D as a read-only outline first — the board's data, flattened, with dates in columns. Prove the two views agree before making it editable.
  3. Turn on editing: Tab, Shift+Tab, Enter, inline dates. Delete the wizard the day this lands.
  4. Fold the orphans into D's header — rename, client, project state, billing type. All four currently have no home or a five-step one.

What I'd cut regardless of which option you pick

  1. The Milestones step. Separate table, separate strip, and you don't fill it in. Phase end dates already carry the meaning.
  2. The wizard's Tasks textarea. Strictly weaker than the composer it hands off to.
  3. The "Serves a bet?" chips at creation. Move to the planning surface, where Targets are actually in view.
  4. The template mode switch at 10+ projects. It appears without explanation at an arbitrary threshold, and it silently overwrites the category you just chose.
