Kash 3.2 · design options · part two

Plan mode, and where project-level editing lives

Decided: create in place on the index (plus a command palette entry), Plan mode as a second view of the same data, columns for due date / estimate / logged, priority stays an inline indicator, composer syntax kept as a paste path but demoted.

Part one

Plan mode, drawn

Same project, same data, second view. The tree is built with Tab and Shift+Tab instead of ;;; and Parent//+ Child. Three right-hand columns; estimate and logged roll up to the phase row so a phase tells you its own story without opening the burn panel.

Indent is the grammar.A row at the top level is a phase. Indent it and it becomes a task. Indent a phase under a phase and you get the sub-phase the schema already supports. Nothing to memorize, nothing hidden behind a chip.
Estimate and logged roll up.Data model rebuild shows 12h estimated against 14h logged, in crimson, without opening the burn panel. That is the burn signal you built in W15, moved to where you would actually see it.
Due on a phase is its end date.One date per phase row, not a start and an end. Start is inherited: today for the first phase, the previous phase's end for the rest. You said dates start today with no end, so the empty state reads "set end" rather than showing a fabricated one.
The one risk.Three numeric columns on every row is dense by this design system's standards. If it reads busy in build, logged is the one to hide until it is nonzero.
Part two

Where rename, client, state and billing live

Four things with no good home today. Rename costs five steps. Client is never asked. Project state — prospect, active, paused, done — exists in the schema with no control anywhere in the app. Billing type is buried in the burn panel. Here is each option in practice.

Option 1

Inline on the board header

Click the title to rename. Chips for the rest.

In practice

  • Rename goes from 7 interactions to 2. Click, type.
  • State becomes visible at a glance on every project, which is the point of having the field.
  • Everything is on the surface you are already looking at, every day.

Trade

  • Four controls in the working header. This design system is aggressive about keeping the doing surface quiet.
  • Billing type sitting next to the project name reads like the project is about money.

Option 3 · recommended

Split by how often you touch it

Rename and state inline. Client and billing in Plan.

Great White Q4 reporting Active
Great White 18h logged 62% done
client and billing live in Plan
BoardPlan
Two editable controls on the header. Two facts, read-only.

In practice

  • Rename is one click on the title, because you do it often and it should cost nothing.
  • State is a single chip on the right, because it changes rarely but you want to see it constantly — pausing a project is a decision, and an invisible one is a lie.
  • Client and billing move into Plan mode's strip. You set them roughly once per project, and they belong next to money and scope, not next to the name.
  • The client name and hours stay on the header as plain text, not controls — visible without being editable.

Trade

  • Two locations to remember instead of one. Mitigated by the rule being legible: if it's a fact you change weekly it's on the header, otherwise it's in Plan.

In practice

  • Smallest change to what exists. The overflow menu keeps its job, the wizard just becomes an autosaving panel.
  • Nothing is added to the board header at all.

Trade

  • Rename is still three interactions and still hidden behind a ⋯ menu, which is the specific complaint that started this.
  • State stays invisible until you open the panel, so it stays unused.
  • It is a better wizard, not an absence of one.
smallest buildrename still hiddenstate still invisible

Why option 3

The useful rule for placing a control is how often it is touched against how often it needs to be seen. Rename is touched often — it goes where your hand already is. Project state is touched rarely but needs to be seen constantly, which makes it a visible chip rather than a buried field; a paused project that still looks active on the board is exactly the kind of quiet inaccuracy the mission is built against. Client and billing are set once and consulted rarely, so they earn a place in Plan mode and nowhere else.

Option 1 fails only on volume — four controls is enough to make the working header feel like a settings bar. Option 4 fails on the original complaint: it keeps rename behind a menu.

Part three

The composer, demoted but fixed

It stays, because it is how a pasted plan from Claude or from notes arrives. It stops being the way you hand-type a task, because the outline is better at that. Four bugs get fixed on the way.

Now

What it looks like today

taskduepriorityparent dir
add phases and tasks — one per line
↵ to add · ⇧↵ for new line
syntax chip says “add ⌘↵” · imports page says “press ⌘↵”

Broken

  • Three surfaces teach two different submit keys.
  • The tags editor says to use ;tag, which the project parser reads as a due date and rejects.
  • Unqualified lines file into the last phase you drilled into, which is never named — and which changes when you resize the window.
  • The ;;; phase prefix appears in exactly one chip you have to click to see.
Proposed

Paste path, honest about itself

Paste a plan adding to · Reporting layer
Rebuild the rollup query ; sep 24 ; !!
Backfill last two quarters ; sep 26
Sep 24!! Sep 26
title ; due ; priority ; phase — trailing parts optional
2 lines, both valid ⌘↵ add

Changes

  • One submit key everywhere: ⌘↵. Plain Enter makes a new line, which is what a multi-line box should do.
  • The destination phase is stated on the box — "adding to · Reporting layer" — so a bare line has a visible home.
  • The grammar is printed under the field in words, not encoded in four chips you have to decode.
  • The ;tag hint in the tags editor is corrected or the parser learns tags. Either way they stop contradicting.
  • Invalid lines stay in the box with the error attached to the line, not in a status message below the preview.
